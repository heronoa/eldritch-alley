**Date:** 2026-10-14

### 1. What this MR delivers

Four playtest symptoms are fixed, plus two stability bugs found while manually verifying the fourth. **P1** — rotating the camera while aiming an attack or ability silently drops the hit-chance badge and never brings it back on its own; `Escape` now also puts down whatever is armed (mode, ability, preview) from anywhere, so the player is never stuck behind a vanished preview with no way back to the action bar. **P4** — the bot's own tie-break rule made `endTurn` (scored 0, built first in the candidate list) beat any move that neither closes distance nor climbs, which is why a bot that reached a good position just sat there; `endTurn` now scores below any move whenever an enemy is still alive, so the bot keeps advancing instead of defaulting to a pass. A round cap (the other half of P4, and the part that also affects PvP) is **not** in this MR — see §3.

**P2** rebuilds how the client plays a burst of actions. The server already sends one `events`-then-`state` pair per accepted action (confirmed, not the originally-suspected "snapshot instead of events"); the actual bug was that the client applied each pair the instant it arrived, with no pacing, so a bot's several actions stomped each other's tweens before a frame could render them, and a target's HP bar updated the moment a swing *started* rather than when it landed. The fix is a small FIFO (`game/animationQueue.ts`) that plays one accepted action at a time, holding the next until the current one's own cues have had time to finish (`game/cueTiming.ts`, reusing the existing walk/attack/reload timings); a target's drawn health is now held at its old value until the swing's own impact moment (`view/healthHold.ts`, wired through `UnitSprite.expectImpact`); and a bot turn that is a pure skip — nothing to animate — is held on screen for the length of a turn banner instead of flashing by in one frame, so "the bot did nothing" actually reads as something happening. Ability cues reuse the basic attack's recovery time as a stand-in duration (`scenes/effects.ts` has no single exported total yet) — a known, intentionally conservative approximation, not a bug.

**P3** locks the whole action bar — End Turn included — while that queue is still playing or the turn-change banner would still be on screen, and adds a one-press confirmation before `endTurn` is actually sent whenever the unit on turn still has something it could do (skipped automatically when nothing is left, so the existing auto-end-turn countdown is untouched). The plan asked for the confirmation as a MoveChip-style pair of buttons; it shipped instead as the End Turn button relabelling itself to ask once, because MoveChip's click path always sends its action to the server and a local-only cancel does not fit that shape without inventing a second widget — the acceptance criterion (ask before sending) is met, the exact control is simpler than planned.

**The two stability fixes** were found manually casting an ability after moving, not by any automated test (none of this project's automated suites can run a full Phaser scene). First, the game's action panel does not re-enable itself once a lock clears on its own — only another, unrelated redraw (e.g. turning the camera) happened to refresh it, so the game read as permanently stuck; `update()` now notices a lock clearing and pushes the HUD itself. Second, and more serious: an **unrelated**, already-tracked bug (DT-90 — a stale Vite dev-cache bundle makes `hitChanceFor` throw) happened to fire from inside the new queue's event-processing loop, and since nothing was scheduling the queue's own advance timer until that loop finished successfully, the one exception left the queue permanently stuck with the panel locked forever, surviving every camera or zoom interaction. `playStep` now always schedules its advance timer even if applying the step throws, and the hover-preview computation it was throwing from is now itself wrapped so a broken preview loses only its own badge. Neither fix addresses DT-90's own root cause (the stale cache); both make *any* similar failure — this one or a future one — recoverable instead of fatal to the match.

### 3. What this MR does not deliver

Deferred by the plan itself, with where each one is going:

- **The round cap (the other half of P4).** The plan explicitly leaves its exact number and tiebreak rule (HP % vs. units alive, and in what order) as the owner's decision, and raises whether it is needed in M4 at all — there is no PvP yet to camp against — or whether it should wait for M5's own PvP timer design (ADR 0004). Nothing here implements it.
- **An animation-speed or skip-animation setting**, symmetrical to the existing auto-end-turn setting, for players who find the new pacing slow. The plan's own review raises it as an open question rather than a requirement; nothing here adds it.
- **Server-side pacing of a bot's multi-unit burst.** The plan considers this and decides against it for now: the client-side queue alone already fixes the symptom at this roster size (three units per side), and server pacing is listed only as a resilience nice-to-have if that assumption ever breaks.
- **DT-90's own root cause** (the stale Vite dev-cache). This MR makes the *consequence* of that bug (and any similarly-shaped future one) recoverable; the cache itself still needs `rm -rf frontend/node_modules/.vite` after any new export lands in a workspace package, exactly as DT-90 already documents.

### 4. Notes for the reviewer

- **The P2 rewrite is the highest-risk part of this diff, and it is the one that produced both stability bugs.** `MatchScene.ts`'s `handleEvents`/`handleState` were split and re-merged into a queue; read `applyStep` end to end against the "before" version in `git log -p` if anything about event/state pairing looks suspicious — the ordering invariant it depends on (cues are read against the board *before* the action that produced them) is deliberate and documented inline, not an accident of the refactor.
- **DT-90 is real and already tracked**, independent of this MR; it is why the second stability fix exists at all. If it fires again in review (`hitChanceFor is not a function`, or any other "X is not a function" from an engine import), the fix is `rm -rf frontend/node_modules/.vite && npm run dev:frontend`, not a code change.
- **The MoveChip-vs-relabelled-button divergence (§1, P3)** is a judgement call under time pressure, not a discovered constraint — worth the owner's explicit sign-off rather than silent acceptance, since the plan was fairly specific about the visual idiom.
- **Four tests in `MatchScene.test.ts` changed their own input shape**, not just their assertions (see §2) — worth confirming in review that the new shape (`events` always paired with a following `state`) is actually what the real server guarantees, rather than taking it on faith; `backend/game-server/src/battle-room.ts`'s `publish()` is the place that guarantee comes from.
- **This MR has several subjects riding together** (P1, P4, P2, P3, two unplanned stability fixes), against `CLAUDE.md` rule 5. The eight commits on this branch already split along those subjects individually; splitting the branch itself into separate MRs is the owner's call, made after the fact once the stability bugs surfaced mid-verification of P2/P3.
