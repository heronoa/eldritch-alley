# MR — One room per human player, a process-wide cap on how many, and the same-tab guard restored client-side

**Branch:** `fix/rooms`
**Comparação base:** `develop`
**Milestone:** M2-b (published version) — bug found live, against the deployed server
**Ticket(s):** Nenhum ticket aberto. Bug crítico relatado diretamente pelo dono em produção (2026-10-14): "se outro jogador em outro lugar até outro país estiver jogando eu não consigo jogar."
**Data:** 2026-10-14

---

### 1. O que esse MR entrega

Corrige um bug crítico: o servidor inteiro só conseguia rodar **uma partida de cada vez, globalmente**. `BattleRoom` nunca definia `maxClients`, então o Colyseus tratava a sala como tendo capacidade infinita e nunca a travava — qualquer `joinOrCreate`, de qualquer jogador, em qualquer lugar, era roteado para a mesma sala já existente e recusado com `Error('room full')` no `onJoin`. Um segundo jogador real, em outro país, via exatamente o mesmo erro que uma segunda aba do próprio navegador veria. A correção (`backend/game-server/src/battle-room.ts`) é uma linha: `this.maxClients = 1` em `onCreate`, o que faz o Colyseus travar a sala assim que o primeiro humano entra e criar uma sala nova para o próximo `joinOrCreate` em vez de reaproveitar a ocupada.

Essa correção, por si só, tem uma consequência que **não estava em nenhum plano aprovado** e foi descoberta ao preparar este MR, não antes dele: o debt DT-68 (fechado em 2026-10-05) havia decidido deliberadamente **não** usar `maxClients`, justamente porque isso trocaria a string `'room full'` — que o cliente usa para reconhecer "outra aba do mesmo navegador já tem a partida" — por uma mensagem diferente do próprio Colyseus. Rodar a suíte confirmou: com `maxClients = 1`, um segundo `joinById` na mesma sala agora é recusado pelo Colyseus antes mesmo de `onJoin` rodar, com `room "<id>" is locked`, não mais `'room full'`. E pior: como `joinOrCreate` agora cria uma sala nova sempre que a existente está travada, uma segunda aba do mesmo navegador deixava de ser recusada — passava a abrir uma partida própria, exatamente o problema que o DT-67/68 existia para evitar, só que pelo lado contrário.

Como ainda não existe identidade de jogador no servidor (ver a nota de PvP em memória), o dono decidiu resolver essa segunda parte inteiramente no cliente: um novo módulo, `frontend/src/net/tab-lock.ts`, mantém uma trava em `localStorage` (compartilhado entre abas do mesmo navegador, ao contrário do `sessionStorage` por aba já usado para a reconexão do DT-60). A aba que está em partida grava `{ tabId, updatedAt }` e atualiza isso a cada 5 s; uma segunda aba, antes mesmo de abrir um WebSocket, lê essa trava e, se estiver fresca e for de outra aba, mostra direto o aviso "Você já tem uma partida aberta em outra aba" — a mesma cópia que o DT-68 já tinha. Uma trava mais velha que 15 s (três batimentos) é tratada como abandonada, para uma aba que travou não bloquear o jogo para sempre.

A suíte do servidor (`battle-room.test.ts`) também precisou de ajuste: o teste que fixava a string `'room full'` como "contrato com o cliente" agora fixa a string que o Colyseus realmente lança, e o comentário deixa de descrever essa string como um contrato — o cliente não depende mais dela, nem para o caso de mesma aba (resolvido antes do servidor ser chamado) nem para o de jogadores diferentes (que agora é simplesmente uma sala separada, sem recusa nenhuma).

Nenhum plano formal (`.ia_context/plans/*.plan.md`) cobre este branch: o `maxClients` já estava commitado quando a sessão começou, e o resto foi diagnosticado e planejado ao vivo (plano aprovado interativamente, não um arquivo). Esta description é construída a partir desse diagnóstico e da verificação empírica (suítes rodadas, build, e um teste de duas abas de verdade), não de um plano escrito previamente.

Por fim, a pedido do dono: o servidor não tinha nenhum limite para **quantas** salas podiam existir ao mesmo tempo — só `maxClients = 1` por sala, que limita humanos por partida, não partidas por processo. Agora há um teto de 30 (`GAME_SERVER_MAX_MATCHES`, configurável, nunca pelo cliente): acima dele, `onCreate` recusa a sala nova com um erro simples, que o cliente já trata como "Servidor indisponível" sem precisar de nenhuma mudança no frontend. O contador é de módulo, por processo — só soma quando um `onCreate` termina com sucesso, só subtrai em `onDispose`, para nunca vazar uma vaga se algo no meio falhar.

**Ressalva deliberada, não resolvida neste MR:** o teto é por processo, não global. Hoje isso não é problema — dev e stg são instância única, e o prod, mesmo em ECS atrás de load balancer, ainda não tem presence/driver Redis entre processos (ver a nota de deploy em memória; isso é trabalho do ROADMAP para M4+). Se o prod um dia rodar mais de uma task ECS ao mesmo tempo, o teto real vira "30 × número de tasks", não 30 global. Coordenar isso entre processos pediria a infraestrutura Redis que o projeto ainda não tem, e ficou fora de escopo por desproporção ao pedido.

### 2. O que mudou e por quê

| Arquivo | O que mudou | Por que importa |
|---------|-------------|-----------------|
| `backend/game-server/src/battle-room.ts` | `this.maxClients = 1` em `onCreate` (já commitado em `3377a60`) | É a correção do bug crítico: cada partida ganha sua própria sala, em vez de o servidor inteiro ficar preso a uma única partida global |
| `backend/game-server/src/battle-room.test.ts` | O teste `refuses a second human...` agora espera `/is locked/` (a mensagem do próprio Colyseus) em vez de `'room full'`; removida a checagem de log via `console.error`, que não se aplica mais a essa rejeição; comentário reescrito para não descrever a string antiga como contrato com o cliente | A suíte estava vermelha depois do `maxClients`; o guard manual de `onJoin` (`humanSessionId`) continua existindo como defesa redundante, mas não é mais alcançável por nenhum caminho real de entrada |
| `frontend/src/net/tab-lock.ts` *(novo)* | `tryClaim`, `claim`, `release` — a trava em `localStorage`, sempre com `Date.now()` (nunca `performance.now()`, que não é comparável entre abas) | É o mecanismo que substitui o acidente de servidor único como forma de detectar "mesma aba": agora é deliberado, e funciona sem precisar de identidade de jogador |
| `frontend/src/net/tab-lock.test.ts` *(novo)* | Mesmo formato de `game/panSensitivity.test.ts`: storage em memória e storage que sempre falha | Cobre aquisição, renovação, liberação, a janela de 15 s de abandono e o caso de storage bloqueado nunca travar o jogo |
| `frontend/src/title/title.ts` | `tabId` por carregamento de página; `startHeartbeat`/`stopHeartbeat`/`endLock`; `fail` fatorado em `failWith`; a checagem da trava roda em `press()` antes de criar a `Session`; `endLock()` chamado em todo ponto onde a partida desta aba termina (falha de conexão, falha de download do módulo da partida, `resume()`, `pagehide`) | É o fio que liga a trava ao fluxo real: uma segunda aba nunca chega a abrir WebSocket, e a trava é sempre liberada quando a partida desta aba de fato termina |
| `backend/game-server/src/config.ts` | Nova `readMaxConcurrentMatches(raw, fallback)`, mesmo molde de `readPort` | Lê `GAME_SERVER_MAX_MATCHES` do ambiente com a mesma validação (inteiro positivo) e o mesmo padrão de falhar no boot, não em uso |
| `backend/game-server/src/battle-room.ts` | `DEFAULT_MAX_CONCURRENT_MATCHES = 30`; contador de módulo `activeMatches`; `onCreate` recusa com `Error('the server already has N matches open')` quando no limite, e só incrementa ao final, depois de tudo dar certo; novo `onDispose` decrementa | É o teto em si — sem ele, nada limitava quantas salas o processo podia abrir |
| `backend/game-server/src/main.ts` | Lê `GAME_SERVER_MAX_MATCHES` (padrão 30) e passa como opção padrão da sala: `gameServer.define(ROOM_NAME, BattleRoom, { maxConcurrentMatches })` | O terceiro argumento do `define` sempre vence sobre a opção que um cliente tente mandar na própria conexão — o teto não é burlável pelo cliente |
| `README.md` | Linha nova na tabela de variáveis de ambiente para `GAME_SERVER_MAX_MATCHES` | Documenta o novo env var no mesmo lugar que já documenta `GAME_SERVER_PORT` |

### 3. Notas para o revisor

- **O DT-68 está, na prática, revertido e substituído.** A entrada fechada em `technical-debt-closed.md` não foi reescrita — é um registro histórico — mas a decisão que ela documentou ("não usar `maxClients` para não quebrar a string que o cliente lê") deixou de valer: agora usamos `maxClients` e a detecção de mesma aba é outra, inteiramente client-side. Vale uma entrada de debt nova ou uma nota apontando para este MR, mas isso não foi feito aqui — ficou fora de escopo deliberadamente (ver plano desta sessão).
- **Janela de 15 s para uma aba que trava sem fechar.** Se uma aba crasha sem disparar `pagehide` (processo morto, SO forçando o fechamento), uma segunda aba pode ver o aviso de "outra aba" por até 15 s (três batimentos de 5 s) antes de a trava ser considerada abandonada. É uma troca deliberada: sem isso, uma aba morta bloquearia o jogo para sempre.
- **O guard manual em `onJoin` (`humanSessionId`) ficou órfão, mas não foi removido.** Com `maxClients = 1`, ele não é mais alcançável por `joinOrCreate` nem por `joinById` — o Colyseus barra antes. Ele continua correto como bookkeeping (quem é o humano, usado em `onDrop`/`onLeave`/`handleAction`) e como defesa barata caso `maxClients` seja mudado no futuro; só a `throw` de admissão em si é que está, hoje, morta.
- **`Date.now()`, nunca `performance.now()`, dentro de `tab-lock.ts`.** `title.ts` já usa `performance.now()` para o `Flow`/stamp, que é relativo ao carregamento de cada página — comparar isso entre abas diferentes dá um resultado sem sentido. Um futuro ajuste que misture os dois quebra a trava silenciosamente (nenhum teste do `connect-flow` pegaria isso, porque é outro módulo).
- **O teto de 30 partidas é por processo, de propósito.** Ver o parágrafo de ressalva na seção 1 — não há coordenação entre processos porque o projeto não tem presence/driver Redis ainda (M4+ no ROADMAP). Vale uma entrada de debt se/quando o prod passar a rodar mais de uma task ECS ao mesmo tempo, porque o teto efetivo deixa de ser 30 nesse cenário.
