### 1. What this MR delivers

Until today `platform-api` answered `/health` and nothing else, because there was nothing to persist. It now has a real PostgreSQL database: MikroORM over the entities in `src/db/entities`, a first migration that creates `users`, and a migration step that is a **process of its own** (`node dist/migrate.js`) run once before any instance of the API starts. What that unlocks is the rest of M4 — m4-02 injects `ENTITY_MANAGER` and writes the first account, m4-03 brings its three tables as their own migration — and, later, the AWS deploy, whose ECS one-off task runs this same command against RDS. The schema is a file in this repository, which is the property the milestone exists to establish: `synchronize` is never enabled, in any environment, so nothing but a migration ever creates or alters a table.

Four decisions carry consequences a reviewer should see before reading the code. **The manager the container hands out is a fork** (`orm.em.fork()`), not the ORM's global instance — MikroORM refuses context-specific actions through the global one, and a fork is a unit of work with an identity map of its own. The consequence is deferred on purpose: one fork is shared by every consumer, so the first request that writes has to decide whether it forks per request (`RequestContext`, or a request-scoped provider). That belongs to m4-02, where the first write lives, and the module's comment says so. **The migration step takes a PostgreSQL advisory lock** (`8170001`, a constant of this repository rather than a hash of the database name, on a connection of its own) so that two processes starting at the same instant do not race: the second waits, then finds nothing to apply. **Each migration runs in its own transaction**, so a migration that fails half way through leaves neither a half-created table nor a row claiming it ran — and every migration in this delivery is additive, so code running while the step applies never asks for something that is not there. **The entities and the migration are written to agree on column types**, not merely on behaviour: `type: 'string'` is `varchar(255)` to MikroORM where the migration writes `text`, and the CLI reported exactly that drift before it was corrected.

Implementation followed m4-01 closely, with the divergences named rather than silenced. The plan carries them as **D6–D12**, all of them found by running the tooling rather than by reading about it:

- **MikroORM 6, not 7 (D6).** v7 is ESM-only and `platform-api` compiles to CommonJS. Pinned `^6.6.17`.
- **`migrations.snapshot: false` (D8).** MikroORM's default has the migrator write a `.snapshot-<database>.json` next to the migrations for *every* database it touches — one per scratch database the test suite creates (twenty-three of them in a single run), and a write into a running container's filesystem. It also changed what `migrate:create` diffs against, and produced a migration that undid the previous one. Off, and the diff is against the live database. This is also what fixed the two 5000 ms timeouts the migration tests were hitting: the file went from 26.9 s to 7.1 s and its slowest case from 4.3 s to 1.3 s once the snapshot writes stopped. The raised `testTimeout` that was added while diagnosing the symptom was kept only as margin; it was never the cause.
- **The CLI's config lives in `src/` (D9).** Without `ts-node` the CLI reads only a compiled config, and `rootDir: "src"` means `tsc` cannot emit one from the package root. It is `src/mikro-orm.config.ts` → `dist/mikro-orm.config.js`, and the scripts build first, so a generated migration and the runner read the same `ormOptions`.
- **`tsconfig.json` did change (D10).** The plan predicted it would not; it gained `"exclude": ["src/**/*.test.ts"]`, the convention both sibling packages already carry, because the tests use `import.meta`, which `module: "commonjs"` rejects.
- **Three files the plan's file table did not list.** `src/db/migrate.ts` holds `runMigrations` and `src/migrate.ts` holds the process, because a test cannot import a file that calls `process.exit` — and neither a `require.main` nor an `import.meta` guard is available in a package compiled to CommonJS and transformed to ESM by vitest. `src/db/test-database.ts` is the scratch-database helper the integration cases share. `src/mikro-orm.config.ts` is D9 above.
- **`migrate:check` is now a script, and CI runs it (D12).** The command that caught the D11 drift was one a person had to remember to type. CI runs it immediately after the migrate step, against the database the migrations have just produced, so entity metadata and migrations that disagree fail the build instead of surfacing as a wrong query in production. Verified both ways before it was committed: green after a real migration, red with a deliberately wrong column type, green again after the revert.

One deliberate scope note: the first commit of this branch is **not** persistence. It corrects the stale M3 and M3.5 indexes, the M2-b line and `ROADMAP.md`, which is the gate the owner closed on 2026-10-16 — recorded in the index under § Milestone gate. A reviewer who wants `CLAUDE.md` rule 5 kept strictly can lift that material into a PR of its own; it touches nothing the persistence work touches.

### 2. What changed and why

| File | What changed | Why it matters |
|------|---------------|-----------------|
| `backend/platform-api/src/db/orm.ts` *(new)* | `ormOptions(config)` and `createOrm(config)`: the entities listed **by class** rather than by a path glob, `migrations.path` → `dist/migrations` with `pathTs` → `src/migrations`, `transactional: true`, `snapshot: false`; plus `MIGRATION_LOCK_KEY = 8_170_001` | The one place the ORM's options are built, so `dist` and `tsx` agree and nothing has to guess which folder the process runs from. `synchronize` appears nowhere in it |
| `backend/platform-api/src/db/database.module.ts` *(new)* | A `@Global()` Nest module that owns the ORM's lifetime, is read at container build time, closes the pool `OnApplicationShutdown`, and exports `ENTITY_MANAGER` — a **fork** | The API does not finish starting without a usable `DATABASE_URL`, and no feature module needs an `imports:` line to get a manager. | `backend/platform-api/src/db/entities/user.entity.ts` *(new)* | The `users` table: `id uuid default gen_random_uuid()`, `display_name text`, `email`, `avatar_url`, `privacy_version_seen`, `created_at timestamptz default now()`, `last_login_at` | The table every other table in the schema will point at. ### 3. Notes for the reviewer

- **The branch is two commits, not the five the working notes proposed.** `4f64a87` carries the M4 planning artifacts (the spec, the five plans and the index, plus `privacy-terms.input.md`); `6d46297` carries everything else — milestone 0's index corrections, the code, the tests and the docs, under a message that names only the `package.json` scripts and undersells its contents. They touch disjoint files and can be split further without conflict if the review wants it.
- **The migration step is a single point of failure by construction**, and that is the intent: if it fails, no instance starts. ADR 0019 §Consequences says so, and the exit code is what the pipeline reads.
- **Nothing revokes anything on the server side.** Not a property of this MR, but of the delivery it opens (index decision D3: a signed cookie carrying its own state, no Redis, no `sessions` table). Worth knowing before m4-02 is reviewed.
- **A migration's `down()` is written and never run by a deploy.** A rollback goes back to the previous version of the code, which expects the schema it left. The methods exist because MikroORM's `Migration` has them, not because a pipeline calls them.
- **`npm test` with nothing up is not a broken suite.** The integration cases skip themselves with a printed line naming `npm run infra:up`. CI always sets `DATABASE_URL` and therefore never skips — the local skip is a convenience this milestone kept on purpose (D5).
- **The one Portuguese line this delivery did not fix**: `.env.example` still carries a `# Portas locais` section header in an English repository. It is recorded in the index's § Documentation debt and is not this MR's subject.
- **ADR 0018 and 0020 are rows in `docs/adr/README.md` marked "to write"**, deliberately not written here: both belong to m4-02.
